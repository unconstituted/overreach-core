# Progress

One entry per completed stage of docs/BRIEF.md.

- 2026-11-16: repository set up with CLAUDE.md, build brief and reference material (Chapter 1 prototype, HUD and feel-layer experiments, workout files).
- 2026-11-16: **Stage 0 done.** Vite + TypeScript + Vitest + ESLint skeleton. `npm run dev`, `npm test`, `npm run build`, `npm run lint` all work. ESLint blocks DOM globals and Three.js imports under `src/core/`, and the build type-checks the core a second time without the DOM library, so portability is enforced rather than promised.
- 2026-11-16: **Stage 1 done.** Workout engine in `src/core/workout`: model with steady, ramp, interval sets and free ride; `.zwo` parser and writer (own DOM-free XML reader); FIT workout parser and writer on a shared FIT codec in `src/core/fit` (decoder, writer, CRC); a time-stateless `WorkoutRunner` with targets, next step, text events and "spin up in 5" cues. Both reference workouts parse (Storm Front: 52 steps, 60 min; CrushCh1: 37 steps, 35 min, 7 efforts at 100%+). Note: `CrushCh1.fit` and the prototype's interval table in `a_core.js` differ in places (step boundaries and some targets); Stage 4 treats `a_core.js` as the Chapter 1 source, as the brief says.
- 2026-11-16: **Stage 2 done.** `src/core/record`: a 1 Hz `RideRecorder` driven by the caller's clock (power, cadence, heart rate, game speed, realistic bike speed and distance from a flat-road physics model, lap markers); `summarise` (duration, average and normalised power, kJ, IF, TSS, heart rate, time in power and HR zones); and a FIT activity encoder (file_id, file_creator, device_info, timer events, records, laps, session, activity, CRC). Tests decode the export with the independent `fit-file-parser` library and check NP and kJ against hand-computed fixtures. Not yet verified: an actual upload to Garmin Connect or Strava (needs a real account upload; listed in the hardware checklist).
- 2026-11-16: **Stage 3 done.** `src/devices`: `PowerSource`, `HeartRateSource` and `ControllableTrainer` interfaces; pure packet code for FTMS (Indoor Bike Data, Control Point, status, power range, features), Cycling Power (with crank-revolution cadence maths) and Heart Rate, all tested against byte fixtures written from the specs; `FtmsTrainer` control logic (write queue, response matching, re-requesting control) shared by Bluetooth and the simulator; Web Bluetooth plumbing with reconnect that restores the last target, and a Cycling Power fallback; `SimTrainer` (speaks real FTMS bytes, ERG lag and noise, a rider who follows targets, manual override, stop pedalling) and `SimHeartRate` (lags power by about 30 s, slower recovery, drift); `DeviceManager`; and a device test page at `devices.html`. The Bluetooth code is tested against a fake GATT stack only: it has never met a real trainer. See `docs/TESTING-WITH-HARDWARE.md` (Stage 6).
